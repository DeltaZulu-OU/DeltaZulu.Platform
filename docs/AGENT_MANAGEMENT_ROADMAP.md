# DeltaZulu agent management roadmap

The agent management capability will provide centralized lifecycle control for DeltaZulu agents without turning the agent into a general-purpose remote execution platform. The priority is to make collection reliable, observable, configurable, and safe across tenants and agent groups. The roadmap starts with identity, enrollment, heartbeat, policy delivery, and operational health, then expands into controlled diagnostics, staged rollout, local enrichment, and upgrade orchestration.

This roadmap is independent of the platform core phases defined in [`ROADMAP.md`](ROADMAP.md). It has its own priority scheme and does not block or depend on the platform's Analytics/Governance/Operations phase sequence.

Priorities are `P0`–`P3` (roughly dependency-ordered, earlier phases enable later ones), `Out of scope` for capabilities deliberately not planned, and `Production gate` for capabilities that are required before a production ship but are explicitly **not** required for POC/MVP. `Production gate` rows are not part of the P0–P3 sequence and must not be read as deferrable — they are called out separately precisely so they cannot be silently pushed to "later" the way a low-priority P3 item might be.

| Priority | Phase | Capability | Description | Outcome |
| --- | --- | --- | --- | --- |
| P0 | Foundation | Agent identity model | Define `TenantId`, `AgentId`, certificate identity, hostname, OS metadata, agent version, and first/last seen timestamps. | Every agent has a stable, auditable identity. |
| P0 | Foundation | Automated enrollment | Implement bootstrap-token enrollment that exchanges a short-lived onboarding token for a tenant-scoped agent identity and certificate. | New customer onboarding can automatically provision agents without manual PKI work. |
| P0 | Foundation | Heartbeat endpoint | Agents periodically report version, platform, policy hash, source status, buffer state, output state, and last successful send time. | The platform can distinguish healthy, degraded, stale, and offline agents. |
| P0 | Foundation | Agent inventory view | Build a basic UI/API view listing agents by tenant, group, OS, version, status, last seen, and assigned policy. | Operators can see the managed fleet and identify coverage gaps. |
| P0 | Configuration | Declarative policy model | Define agent policies for inputs, channels, filters, buffer settings, RELP/TLS output, compression, and heartbeat intervals. | Agent behavior becomes centrally defined and versioned. |
| P0 | Configuration | ETW provider profile contracts | Define ETW envelopes, provider profiles, collection policies, decode results, session health, replay sources, filtering, loss accounting, and bounded discovery controls. | Windows ETW collection can use adapters without locking Agent or Platform to a single ETW library. |
| P0 | Configuration | Policy assignment | Allow policies to be assigned to tenants, groups, or individual agents. | Different server classes, environments, and tenants can use different collection profiles. |
| P0 | Configuration | Effective configuration reporting | Agents report the exact applied policy version and configuration hash. | The platform can detect configuration drift between intended and applied state. |
| P0 | Reliability | Source health reporting | Agents report per-source status, including enabled channels, read errors, bookmark state, lag, and last event timestamp. | Collection failures become visible before detection coverage is affected. |
| P0 | Reliability | Buffer health reporting | Agents report memory queue, disk queue, dropped records, retry count, and backpressure state. | Operators can detect forwarding, storage, and network pressure. |
| P1 | Operations | Command queue | Add a constrained command model for one-shot operational actions such as reload configuration, test output, flush buffer, collect diagnostics, and restart service. | Operators can remediate common agent issues centrally. |
| P1 | Operations | Command result store | Persist command status, timestamps, structured output, errors, timeout state, and requesting user. | Operational actions become auditable and supportable. |
| P1 | Safety | Command allowlist | Restrict remote commands to predefined safe operations. Avoid arbitrary shell, arbitrary script execution, or unrestricted local queries. | Agent management remains operationally useful without becoming an unsafe remote execution channel. |
| P1 | Configuration | Policy validation | Validate policy syntax, allowed inputs, buffer limits, endpoint settings, and incompatible options before rollout. | Bad configuration is rejected before it reaches endpoints. |
| Out of scope | Configuration | Canary rollout | Staged rollout is an operational practice, not a platform capability: operators assign new content to a pilot group first using the existing group-scoped assignments and explicit group membership, then widen the assignment. | No dedicated canary feature is planned in any phase. |
| P1 | Configuration | Rollback | Preserve previous policy versions and allow rollback at tenant, group, or agent level. | Failed rollouts can be reversed quickly. |
| P1 | Monitoring | Fleet health dashboard | Aggregate agent health by tenant, group, OS, version, policy, source status, and buffer pressure. | Operators can prioritize remediation at fleet level instead of reviewing agents one by one. |
| P1 | Monitoring | Drift and stale-agent detection | Flag agents that stop checking in, run old versions, fail to apply policy, or report unexpected source state. | Silent degradation becomes visible. |
| P2 | Security | Certificate lifecycle automation | Automate certificate issuance, renewal, revocation, expiry monitoring, and rotation. | PKI remains a backend concern and does not burden customers. |
| P2 | Security | Tenant isolation controls | Enforce tenant-scoped agent identity, tenant-scoped policies, tenant-scoped commands, and tenant-scoped results. | Cross-tenant management mistakes are prevented by design. |
| P2 | Security | Management-plane audit log | Record enrollment, policy changes, command requests, command results, certificate actions, and administrative access. | Agent management actions become reviewable and compliance-friendly. |
| P2 | Local context | Diagnostic providers | Add predefined local checks for service status, event-channel availability, Sysmon channel presence, agent permissions, disk state, and network reachability. | Support teams can diagnose common endpoint issues without logging into the host. |
| P2 | Local context | Local enrichment providers | Add controlled providers for installed software, drivers, browser extensions, local users, and selected system facts. | Agent-collected telemetry can be enriched without requiring a separate endpoint inventory product. |
| P2 | Data quality | Telemetry utilization metrics | Report collected, filtered, forwarded, dropped, retried, and suppressed event counts by source and policy. | The platform can measure collection quality and wasted telemetry. |
| P2 | Data quality | Collection recommendation engine | Use deterministic health and utilization metrics to suggest source, filter, and policy improvements. | Operators receive actionable recommendations instead of raw health signals only. |
| P2 | Data quality | ETW trace replay harness | Replay captured Windows Event Trace Log (`.etl`) fixtures through the same ETW envelope, decoder, normalizer, and detection test path used by production telemetry. | Parser drift and detection regressions can be reproduced across Windows builds. |
| P3 | Lifecycle | Agent upgrade orchestration | Support version rings, staged rollout, upgrade status, and rollback for agent *binary* upgrades. Must reuse the TUF root of trust established by the `Production gate` rows below rather than introduce a second, independent signing scheme. | Agent upgrades become centrally controlled, observable, and signed under the same root of trust as agent content. |
| P3 | Lifecycle | Compatibility matrix | Track which agent versions support which policy schema versions, input types, commands, and protocol features. | Rollouts avoid incompatible configuration and protocol combinations. |
| P3 | Advanced operations | Maintenance windows | Allow policy rollout, upgrade, and disruptive commands to respect tenant or group maintenance windows. | Operational changes align with customer change-control requirements. |
| P3 | Advanced operations | Advanced local query abstraction | Expose selected local resource providers through a constrained query interface with limits, RBAC, audit, and timeout controls. | Analysts and operators can inspect endpoint context safely without arbitrary endpoint execution. |
| P3 | Advanced operations | Multi-region management support | Support regional management endpoints and tenant affinity for larger deployments. | The management plane can scale across customer regions and data-residency boundaries. |
| Production gate | Security | TUF client conformance evaluation | Run the candidate client/repository library (`tuf-dotnet`, NuGet package `TUF`) against the official TUF conformance test vectors; assess its maintenance and adoption signal. Fall back to a from-spec implementation of the client verification subset if it fails the bar — skipping the control is not an acceptable fallback. | The single highest-risk component of this whole effort (client-side signature/rollback/freeze verification correctness) is checked before any production key ever depends on it. |
| Production gate | Security | Root-of-trust key management | Stand up the TUF root role: initial threshold-1 key held outside every online process (Platform.Web included), a documented rotation procedure per the TUF spec, and an explicit, owner-assigned decision on physical/HSM custody. | There is a real, auditable root of trust instead of an implicit "the database is the truth" assumption. |
| Production gate | Security | Targets-role content signing | Sign accepted `ResourceProfileVersion`, `DaemonConfigVersion`, and resolved `PolicyBundle` content with a TUF targets key held outside `DeltaZulu.Platform.Web`; wire the signing step into Governance's existing proposal/review/accept gate rather than the request pipeline. Replace the caller-supplied, unverified `ContentHash` fields with real hashes over the signed content for anything shipped to production. | A compromised Platform API process cannot forge trusted agent content; content authenticity survives a full web-tier compromise, not just transport-layer TLS. |
| Production gate | Security | Timestamp/snapshot-role freshness signing | Sign the heartbeat's `desiredBundleId`/`desiredBundleHash`/`policyChanged` freshness claim (TUF timestamp role, `version`/`expires` fields added) and a new manifest of current targets-file versions (TUF snapshot role), both with an online key scoped to nothing but this signature. | Rollback, indefinite-freeze, and mix-and-match attacks against the policy pull protocol are structurally blocked, not merely made inconvenient. |
| Production gate | Security | Agent-side verification gate | Build `DeltaZulu.Agent`'s bundle-apply path (not yet implemented) with full TUF client verification as a hard precondition to applying any bundle — no warn-only or reduced-trust fallback mode. | Agents cannot be tricked into applying forged, rolled-back, or stale configuration even if the transport or an intermediate cache is compromised. |
| Production gate | Security | Production-ship gate enforcement | Add an explicit environment check that refuses to serve unsigned policy bundles when the platform is configured for production, while leaving POC/MVP/development deployments unaffected. | TUF adoption cannot be silently skipped by a production deployment the way an unenforced roadmap item could be. |

The implementation order should start with P0 identity, enrollment, heartbeat, policy assignment, health reporting, and ETW provider profile contracts. These capabilities create the minimum viable control plane and the abstraction needed to evaluate ETW implementations behind adapters. P1 should then add constrained operations, rollout safety, and fleet-level visibility. P2 should improve security, auditability, local context, telemetry-quality measurement, and ETW trace replay validation. P3 should focus on mature lifecycle management, controlled local querying, maintenance windows, and scale.

The `Production gate` rows depend only on P0 (content delivery, already implemented) and P1 (the command queue, already implemented); they do not need to wait for P2/P3 to start. See [ADR 0015](adr/0015-tuf-agent-content-signing.md) for the full design rationale and role mapping. POC/MVP deployments may ship and keep shipping unsigned policy bundles exactly as today — these rows gate a *production* release, not the next demo.

## Implementation status

The P0 minimum viable control plane is implemented (see [ADR 0012](adr/0012-agent-control-plane-pull-protocol-and-auth.md) and [`architecture/agent-control-plane.md`](architecture/agent-control-plane.md)): agent identity with per-agent hashed credentials (certificate identity fields reserved for the P2 PKI work), bootstrap-token enrollment, the heartbeat endpoint feeding `internal.AgentObservations`, the agent inventory and fleet views, declarative policy delivery through lazily resolved content-hashed policy bundles (`/api/agent/v1` pull protocol), policy assignment at tenant/group/agent scope with explicit group membership, effective-configuration reporting with drift derived in the lake `AgentLatest` view, buffer-state reporting via heartbeat metrics, and per-source health reporting into `internal.SourceObservations` (bookmark state and lag remain agent-side work). From P1, the constrained command queue with its result store and allowlist is implemented ([ADR 0013](adr/0013-constrained-agent-command-queue.md)), along with enrollment rate limiting (10 requests per remote address per minute), the fleet health dashboard (`/agents/fleet` rollups by group, version, and policy bundle) and drift/stale detection (lake views plus the inventory sweep). Policy validation is enforced before rollout (blocking findings reject the Draft → Validated transition for both resource profiles and daemon configs), and rollback is available at tenant, group, or agent level through per-assignment version pins that resolution honors with the usual scope specificity. With that, P1 is complete; canary rollout is out of scope as an operational concern (staged rollout is performed with the existing group-scoped assignments rather than a dedicated platform feature).

From P2, telemetry utilization metrics are implemented for the collected/filtered/forwarded/dropped axes named in the roadmap (see [`architecture/agent-control-plane.md`](architecture/agent-control-plane.md#telemetry-utilization-metrics)): fleet-wide forwarding yield, wasted volume, forward failure rate, and read error rate; a per-source ranking by wasted volume; a rollup by resource profile (the "by policy" axis); and an agent-level buffer drop ratio distinguishing true data loss from intentional filter discard. Retried and suppressed event counts are not yet reported — no retry telemetry is emitted today, and discards carry no reason code to distinguish a suppression rule from ordinary filtering — so those two roadmap terms remain open, along with trend/velocity metrics and byte-volume measurement. The collection recommendation engine (the next P2 row) is unimplemented and would consume these metrics as its input. A development simulator (`tools/DeltaZulu.Agent.Simulator`) exercises the full enroll → heartbeat → pull → ack loop including command execution and source health.

**`Production gate` status: not started, not yet required.** A security review found that `PolicyBundle.ContentHash`, `ResourceProfileVersion.ContentHash`, and `DaemonConfigVersion.ContentHash` do not provide the integrity guarantee their names imply — the bundle-level hash covers only the contributing version IDs (a dedup key, not a payload hash), and the per-version hashes are caller-supplied strings nothing verifies. No signature exists anywhere in the pull protocol today, and there is no agent-side apply/verify path yet to enforce one. [ADR 0015](adr/0015-tuf-agent-content-signing.md) records the decision to close this with a TUF-mapped signing scheme (targets/timestamp/snapshot/root roles) before production, with concrete subtasks listed above under the `Production gate` priority. This does not block POC/MVP: unsigned bundles keep working exactly as today until those rows are implemented and the production-ship gate (last row above) is turned on.
